# 03 · 工具设计

工具是模型与系统之间的契约。设计得好，模型一次调对；设计得差，模型反复试错、乱传参数、把错误当结论。

## 名字与描述

- 名字用动词开头、能望文生义：`search`、`read_text`、`fetch_url`，不要 `do_stuff`。
- 描述写三件事：**做什么、参数含义、返回什么**。参数的边界（1～20、相对路径）写进描述，比让模型猜更可靠。
- 不要在一个工具里塞多种行为。`files` 服务器拆成 list/read/write/stat 四个工具，而不是一个带 `action` 参数的万能工具。

## 参数 schema

- 用具体类型：`int`、`bool`、枚举，而不是全用 `str`。
- 给默认值，并在描述里说明默认行为。
- 对数量、长度设上限，服务端再校验一次；schema 只是提示，不是安全边界。

## 返回什么

- 返回结构化数据（dict/list），比拼一段自然语言更容易被模型正确使用。
- 大结果要分页或截断，并显式标注 `truncated` / `offset`，否则模型会把截断当成全部。
- 失败返回可读原因：`NOT_FOUND`、`INVALID_ARGUMENT`、`PATH_ESCAPE`。模型看到「路径越出根目录」会换路径；看到「500 Internal Server Error」只能瞎猜。

## 幂等与副作用

- 读操作尽量幂等；写操作要显式命名（`write_text`），并在描述里说明会改什么。
- 删除、覆盖、执行命令这类不可逆操作，默认不做；必须做时加确认与审计。
- 不要让「查询」悄悄产生副作用，例如 search 顺带写缓存文件。

## 错误处理

本实验室的做法：核心层抛 `ToolError(code, message)`，服务器层转成 `ValueError`，由 FastMCP 返回 `isError=true` 与文本。这样单元测试可以直接断言错误码，协议层也能把原因带给模型。

## 练习

1. 给 `search` 增加 `offset`，并想清楚它与 `limit` 的组合语义；
2. 给 `read_text` 增加 `start_line` / `end_line`，避免只能从头读；
3. 设计一个 `kb://doc/{id}` 资源，比较它和 `get_document` 工具的差异。
